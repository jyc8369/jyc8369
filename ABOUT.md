<details>
<summary><strong>Read this section as text</strong></summary>

I build software around friction I can actually see. I usually start with repetitive, inconvenient, or unnecessarily complicated workflows, then turn that friction into focused tools or small services that I can actually use.

1. **Notice real friction** — Start from a concrete inconvenience rather than a feature list. Look for repetition, confusing steps, and wasted time.
2. **Build a usable fix** — Keep the scope small enough to understand, but complete enough to be useful in practice. I tend to build utilities, developer tools, and automation around that goal.
3. **Learn from operation** — Deploy what I build and pay attention to what becomes difficult once software leaves localhost. Failures become feedback for the next design, deployment, and operational decision.

My current direction is **DevOps**, **Systems Engineering**, and **Reliability**. Long term, I want to connect development decisions with reliable system operation and the real needs of the people using the software.

</details>

Convenience and efficiency are the starting point for how I think about software. Useful software should remove unnecessary work instead of simply moving complexity onto the user.

- **Convenience** — Reduce unnecessary effort so the user can focus on the task they actually care about.
- **Efficiency** — Prefer fewer steps, less repetition, and a faster path to the same reliable result.
- **Practicality** — A small project is valuable when it solves a clear problem and fits into a real workflow.
- **Iteration** — Ship a usable version, observe the next source of friction, and improve the workflow step by step.

I prefer clear workflows, practical results, and improvements that can be felt directly by the person using the software.

</details>

## Learning Through Small Services

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="./assets/profile/lifecycle-dark.svg">

<details>
<summary><strong>Read this section as text</strong></summary>

I learn by taking small services through the full operating loop: **Build → Deploy → Observe → Debug → Improve**. Building the software is only the first part; I want to understand what happens when it runs in a real environment and something eventually goes wrong.

Through that loop, I focus on three kinds of learning:

- **Deployment reality** — What changes outside localhost, and what kinds of environments make development and deployment easier.
- **Useful signals** — Which logs, metrics, and pieces of system state are actually useful when diagnosing an incident.
- **Operational leverage** — Where automation, prevention, and better tooling can remove repetitive operational work.

The areas I am currently exploring through this process include **CI/CD, Linux, Containers, Networking, Observability, and Reliability**.

</details>
